# Выпуск и возврат центра аккредитации

21 ноября 2026 · Исполнитель: Кодекс Астра 6

Рабочий профиль основной редакции описан в [compose.release.yml](../compose.release.yml). [Протокол репетиции](../../docs/modernization-audit/10-RELEASE-REHEARSAL.md) фиксирует, какой кандидат испытан и что остаётся открытым. До производственных действий владелец системы подтверждает окно, ответственных за базу и медиа, условия переключения и критерии возврата.

## 1. Опознать работающую систему

Ответственный за эксплуатацию фиксирует digest приложения и фронтенда, версию PostgreSQL, версию схемы и места хранения БД и медиа. На действующем сервере достаточно передать название редакции, номера миграций и идентификаторы образов. Пароли, строки подключения, ключи, session id, дампы и файлы участников остаются в закрытом контуре. При заранее разрешённой диагностике DBA может получить номера этим запросом в своей сессии чтения.

```sql
BEGIN READ ONLY;
SELECT app, name
FROM django_migrations
WHERE app IN ('eventproject', 'directories', 'qr_event')
ORDER BY app, name DESC;
ROLLBACK;
```

Дата последней записи миграции сама по себе не идентифицирует исходники. Для корневой схемы проверить переход от 0008 с шифрованием ИИН и изменёнными полями мероприятия. Для вложенной редакции сверить уже применённые миграции и отсутствующие. Расхождение фактической схемы с учётом Django останавливает автоматический перенос до разбора DBA. [Миграция шифрования](../eventproject/migrations/0009_attendee_iin_encrypted.py)

## 2. Зафиксировать точку восстановления

- Согласовать RPO — допустимую потерю записей и файлов, и RTO — допустимое время простоя. Протокол короткой синтетической репетиции даёт исходное измерение для этой конкретной выборки.
- Остановить поступление изменений на согласованное окно. Учитывать браузерные формы, фоновые импорты, внешние подтверждения, загрузки файлов и экспорты. Дождаться уже начатых транзакций и записи медиа. Записать момент отсечения в UTC.
- Снять согласованные резервные копии БД и `MEDIA_ROOT`. Архив `pg_dump -Fc` сохраняет снимок одной БД. Файловое хранилище, роли кластера, параметры сортировки, нужные расширения и владелец томов требуют отдельной фиксации. Для архивов БД и медиа записать размеры и контрольные суммы, ограничить доступ, включить шифрование. [Документация pg_dump](https://www.postgresql.org/docs/15/app-pgdump.html)
- Записать версии и порядок ключей Fernet и версии служебных секретов в отдельном защищённом хранилище. Дамп старой схемы может содержать открытые значения. При ротации учесть все потребители исторически раскрытого пароля БД. Откат не должен вновь включить раскрытые учётные данные.
- Поднять другую БД и отдельный каталог или том медиа, восстановить архив через `pg_restore --exit-on-error`, подключить соответствующие ключи. Сверить количество записей по ключевым таблицам, доступность связанных файлов, чтение зашифрованных полей и отрицательную проверку доступа. Для доказательства достаточно чисел, контрольных сумм и статусов. [Документация pg_restore](https://www.postgresql.org/docs/15/app-pgrestore.html)

## 3. Принять точный Linux-кандидат на отдельном стенде

Для стенда использовать выделенный Docker Engine, уникальное имя Compose-проекта, пустые тома, тестовый домен, синтетические записи и отдельные TLS/служебные ключи. В примере переменная `REHEARSAL_ENV` содержит путь к закрытому файлу с тестовыми параметрами, `REHEARSAL_PROJECT` — уникальное имя этой репетиции. Секреты размещают за пределами контекстов сборки. Обычный `docker-compose.yml` запускает dev-профиль.

```sh
set -eu
: "${REHEARSAL_PROJECT:?set a unique rehearsal project name}"
: "${REHEARSAL_ENV:?set the absolute path to the synthetic rehearsal env file}"
release() {
  docker compose -p "$REHEARSAL_PROJECT" --env-file "$REHEARSAL_ENV" -f compose.release.yml "$@"
}
release config --quiet
release build
release up -d --wait db
release run --rm --no-deps app python manage.py migrate --plan
```

На отдельной синтетической БД применить запланированную схему, подготовить таблицу общего кэша и проверить готовность. Профиль запуска приложения каждый раз проверяет миграции и доступность таблицы.

```sh
release run --rm --no-deps app python manage.py migrate --noinput
release run --rm --no-deps app python manage.py createcachetable
release run --rm --no-deps app python manage.py check_release_schema
release up -d --wait
release ps
```

Внешняя точка входа этого профиля слушает loopback. Доверие к заголовку HTTPS рассчитано на прокси, который сам его устанавливает. Сертификат должен покрывать фактический домен, доверенная почта и origin активации настраиваются до выдачи приглашений. В качестве проверки оператор открывает `/workspace/`, входит, читает назначенное синтетическое вложение, выходит и проверяет закрытие доступа. Проверить отказ при неподготовленной схеме, сохранность после перезапуска, состав образов, SBOM и записанные решения по оставшимся уязвимостям. Сохранить digest либо локальные image ID испытанного комплекта. Для промышленного окна брать те же проверенные образы по идентификатору. Повторная сборка с изменившимися системными пакетами требует новой проверки.

## 4. Условия запуска и отката

До открытия записи владелец подтверждает ротацию действующих секретов, согласованность резервных копий, испытание восстановления, график отката, полномочия супероператоров и потребности мероприятия в QR и официальном файле выгрузки. QR в данном кандидате приостановлен, четыре исторических JSON служат для сверки. Для договорной выдачи нужны согласованные поля, канал и получатель.

Остановить переключение при расхождении контрольных количеств, ошибке чтения шифрованного поля, пропаже связанного файла, нарушении прав или неготовности схемы. До возобновления записи проще вернуть трафик к прежнему сохранённому комплекту приложения, БД и медиа. При наличии записей после точки отсечения DBA согласует их перенос и сверку с владельцем процесса, прежде чем возвращать пользователей. Восстановить согласованные ключи, использовать актуальные реквизиты БД и отозвать старые сессии, если возвращаемая версия не понимает поколения отзыва. Проверить обычный новый вход, запрет ранее отозванной сессии, доступ назначенного оператора и отказ постороннему. После проверки зафиксировать действительные RPO/RTO, решение о возврате доступа и список открытых расхождений.

Миграции 0025–0029 (линия `security-hardening`: журнал действий, иерархия мероприятий, флаги проблем, счётчик возвратов) только добавляют таблицу, поля и индексы. Таблица `AuditLog` защищена триггером PostgreSQL от изменения и удаления строк. Откат к 0024 удаляет журнал действий: перед ним выгрузить его для архива. Ноябрьские миграции после сведения линий получили номера 0030–0035 (были 0025–0030); на рабочих базах они не применялись.

Миграция 0032 (пакеты выгрузки) добавляет в `ExportLog` обязательный `package_id` без значения по умолчанию на стороне БД. Код до 0032 не сможет записать новую выгрузку в такую схему, поэтому возврат приложения к версии без 0032 выполняется только вместе с `migrate eventproject 0031`. Откат удаляет состав, манифест и подтверждения получателя: перед ним выгрузить список пакетов (`package_id`, `attendee_ids`, `acknowledged_at`) для сверки с получателем. Сами участники и их статусы не меняются.

Миграция 0033 (решение проверяющего) добавляет участнику обязательное `review_comment` без значения по умолчанию на стороне БД, поэтому код до 0033 не сможет создать участника в такой схеме. Возврат приложения к версии без 0033 выполняется вместе с `migrate eventproject 0032`. Откат удаляет причины возврата, видимые операторам: перед ним выгрузить список участников в статусе `draft` с непустой причиной.

Миграция 0034 (квитанции импорта партнёров) только добавляет таблицу; старый код её не читает. Возврат к версии без 0034 возможен и без отката схемы, но тогда повторно присланные анкеты снова будут обрабатываться заново, а дубли — по старому правилу (транскрипция). Откат схемы — `migrate eventproject 0033`, он удаляет историю подтверждений. Перед первым запуском импорта на новой версии убедиться, что нет параллельно работающего старого cron-импорта.

Миграция 0035 только создаёт индекс `attendee_dateadd_idx` (`CREATE INDEX`, не `CONCURRENTLY`): на время построения запись в таблицу участников блокируется. На 150 тыс. строк в PostgreSQL 15 миграция заняла около 1 с. Если таблица в рабочей БД значительно больше, DBA заранее оценивает время по числу строк. Откат — `migrate eventproject 0034`, данные не меняются; старый код индекс не использует и не мешает ему.

Миграция 0036 удаляет `Attendee.last_return_reason` — дубль `review_comment`. Перед удалением текст причины переносится в `review_comment`, если тот пуст (возвраты до сведения линий), поэтому причины не теряются. Откат — `migrate eventproject 0035`: причина возвращается в `last_return_reason` у участников с `return_count > 0`.
